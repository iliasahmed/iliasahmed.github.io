Codex repository guidance — Ilias Ahmed Portfolio
Start here
Read CODEX_PORTFOLIO_MASTER_BRIEF.md in full before planning or editing the site. It contains the approved direction, CV-based biography and employment timeline, project descriptions, service positioning, visual system, architecture, publishing constraints and definition of done. Use it as the task specification, not as copy to paste verbatim into the site.
Working rules
- Build a finished, tasteful client-facing mobile and full-stack engineering portfolio, not a recruiter-only CV or unfinished wireframe.
- Source employment claims, metrics and skills from the master brief and original supplied CV. Do not invent testimonials, screenshots, customer results, employer endorsements or shipped full-stack products.
- Distinguish employer work from independently delivered client work. Keep uncertain full-stack details reviewable rather than pretending to verify them.
- Use React, TypeScript, Vite, current Tailwind Vite integration and static GitHub Pages hosting unless the existing repository provides an equivalent established setup.
- Prefer semantic accessible UI, mobile responsiveness, fast loading, real contact links and reusable typed content data.
- Ensure GitHub Pages navigation and direct project-case-study links work without server rewrites.
- Inspect the repository before changes. Do not overwrite existing user work unnecessarily.
- Do the work end to end and run the actual lint/typecheck/build/tests available. Report what was and was not tested. Never claim deployment if GitHub access is unavailable.
- Keep user-facing copy simple, factual and confident. No hype, filler, generic stock portraits, fake product screenshots or broken placeholder CTAs.
Final deliverables
Implement the site, a GitHub Actions Pages workflow, README, content editing instructions and a CONTENT_REVIEW.md with any unresolved owner approvals. Tell the user how to run and publish it, and summarize tests actually executed.
